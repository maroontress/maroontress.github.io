生成AIによるコード補完

先日、日本のGitHubのワークショップに参加してきた。内容は主にVS CodeでGitHub Copilotの使い方を紹介するものだった。コード補完も進化していて、クラス名を変更すると、そのクラスの実装を「名前の変更に応じて」変えるように促すという例を紹介していた。具体的には、次のコード:

import math

class Point2D:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def distance_to(self, other):
        dx = self.x - other.x
        dy = self.y - other.y
        return math.sqrt(dx * dx + dy * dy)

    def __str__(self):
        return f"Point2D({self.x}, {self.y})"

のPoint2DをPoint3Dに変えると、つまり2を3に変えると、次のようにCopilotが次々に変更を提案してくる:

  • __init__: パラメータにzを追加、最後の行にself.z = zを追加する。
  • distance_to: dz = self.z - other.zを追加、math.sqrtの引数の最後に+ dz * dzを追加。
  • __str__: 返す文字列を f"Point3D({self.x}, {self.y}, {self.z})"に修正。

提案を全て受け入れると、次のようなコードに変わった:

class Point3D:
    def __init__(self, x, y, z):
        self.x = x
        self.y = y
        self.z = z

    def distance_to(self, other):
        dx = self.x - other.x
        dy = self.y - other.y
        dz = self.z - other.z
        return math.sqrt(dx * dx + dy * dy + dz * dz)

    def __str__(self):
        return f"Point3D({self.x}, {self.y}, {self.z})"

繰り返しになるが、2を3に変えた後、私は少し待ちながらタブキーを押しただけで、所望のPoint3Dクラスを手に入れることができた。生成AI、万歳。

だが、それは本当に望ましいことだろうか。

展開されたコード

Point3Dクラスのdistance_toの中のコードを次のように色分けしてみる:

dx = self.x - other.x
dy = self.y - other.y
dz = self.z - other.z

まるで行列の掛け算を展開したような配色だ。 どの行の右辺も、selfの何かから、otherの同じ何かを引いたものだ。 このようなコードは（多分、未だに）名前の無い「スメル」であり、 私は因数分解を展開したようなコードとか、展開されたコードなどと呼んでいる。

概念的には、次のように記載したい:

(dx, dy, dz) = (self - other)⊙(x, y, z)

しかし、相手はPythonなので、私の願望を押し付けても無意味だ。一般的に、多くのオブジェクト指向のプログラミング言語では、「展開されたコード」を次のような手順で「因数分解」できる:

  1. selfとotherを「ペア」とするインスタンスpを作成する（p.leftとp.rightがselfとotherに対応）
  2. selfからx, y, zを取り出すラムダ式のリスト$L$を作成する
  3. リスト内包表記によりf(p.left) - f(p.right)に変換する（fはリスト$L$の要素）

このような蘊蓄をプロンプトに添えて、 distance_toをChatGPTにリファクタリングさせてみると、次のようなコードを示した:

    def distance_to(self, other):
        pair = (self, other)
        accessors = [
            lambda p: p.x,
            lambda p: p.y,
            lambda p: p.z,
        ]
        diffs = [f(pair[0]) - f(pair[1]) for f in accessors]
        return math.sqrt(sum(d * d for d in diffs))

ChatGPTによると、クラスを新しく作る必要はなく、タプルで良いとのこと。であれば、pairは不要であり、pair[0]をself、pair[1]をotherにした方が良い。また、accessorsのリストは毎回作成して欲しくないので、クラス属性にしたい。つまり、次のようにリファクタリングして欲しかった:

from typing import Callable, Self, final
⋮
@final
class Point3D:
    accessors: tuple[Callable[[Self], float], ...] = (
        lambda p: p.x,
        lambda p: p.y,
        lambda p: p.z,
    )
    ⋮
    def distance_to(self, other: Self) -> float:
        accessors = Point3D.accessors
        diffs = (f(self) - f(other) for f in accessors)
        return math.sqrt(sum(d * d for d in diffs))

続けて、ChatGPTは、この因数分解されたコードには次のような利点があると主張した:

  • 保守性: 差分計算ロジックが1か所（dx, dy, dzの重複消滅）
  • 拡張性: 次元を増やすときはアクセサを追加するだけ（例: lambda p: p.w）
  • アルゴリズムとデータ構造の分離: 「何を引くか」と「どう計算するか」が分離されている

さらに、ChatGPTは親切にも、Pythonでは次のようにすればラムダ式すら不要にできると教えてくれた:

coords = ("x", "y", "z")
diffs = [getattr(self, c) - getattr(other, c) for c in coords]

これは、JavaやC#などでリフレクションを使うことに相当する、と理解すればよい。

また、データの持ち方、データ構造を変えることも提案してくれた。コンストラクタを次のように変更する:

class Point3D:
    def __init__(self, x, y, z):
        self.coords = (x, y, z)

こうなると、ラムダ式のリストは不要であり、distance_toは次のように書ける:

    def distance_to(self, other):
        diffs = [(a - b) for a, b in zip(self.coords, other.coords)]
        return math.sqrt(sum(d * d for d in diffs))

ただし、このままでは属性xでx成分を参照することができない。属性xでのアクセスを可能にするには、次のようにすれば良い（y, zも同様）:

    @property
    def x(self):
        return self.coords[0]

とにかく、展開されたコードを因数分解して、重複を消すことができた。しかし、これで終わりではない。このようなコードは実行が遅い（パフォーマンスが悪い）ので、distance_toが短時間に多数呼び出される場合（例えば、秒間100万回など）は、元のコードに戻す必要がある。つまり、distance_toを最適化するため、コードを展開する必要がある。もちろん、展開されたコードが常に高速になるわけではないが、この場合は当てはまる。このようなところが、ソフトウェア開発の難しいところだ。

ただし、そもそもパフォーマンスが重要なのであれば、Pythonならnumpy.ndarrayを使うところから始めるだろう。余程の事情が無い限り、Point2DやPoint3Dのようなクラスを自作するべきではない（学習の題材としては良いが）。

そんなことよりも、私には不思議なことがある。なぜ、生成AIは「展開されたコード」を提案してくるのだろうか。

生成AIが「展開されたコード」を提案する理由

元々のPoint2Dのコードが「展開された」ものだったので、Copilotはそのスタイルに合わせて変更を提案してくれるのではないか、と考える人もいるだろう。しかし、実際はそうではない。コードを次のように書いて、Copilotのコード補完を確認してみると良い:

class Point3D:
    def __init__(self, x, y, z):
        self.x = x
        self.y = y
        self.z = z

    def distance_to(self, other):

distance_toの続きとして、次のように提案した:

        dx = self.x - other.x
        dy = self.y - other.y
        dz = self.z - other.z
        return math.sqrt(dx * dx + dy * dy + dz * dz)

パフォーマンスが重要だからと気を使ってくれているのだろうか。いや、そうではない。生成AIが提示するコードには次のような傾向がある。

1. 学習データ的に「最も典型」なものが選ばれやすい

Point3Dのようなコードの例は、教科書、ブログ、Stack Overflow、入門書などに大量に出現する。そうした例では、距離計算は次のような形で紹介されることが多い:

dx = self.x - other.x
dy = self.y - other.y
dz = self.z - other.z

生成AIは確率モデルであり、このような例を多く学習している。その結果、最も確率が高い提案は「展開されたコード」のパターンになりやすい。

一方、ラムダ式やgetattrを使うコードは、Pythonでは中級以上であり、数学的距離の例としてはまず出てこないため、確率的に負けやすい。

2. 汎用すぎて意味が曖昧になるコードを嫌う

生成AIは基本的に前提が少なく、意味が1行で確定するコードを好む傾向がある。

反対に、設計として高度なコード、すなわち:

  • 変更が容易（Point3Dでいうと、次元数を変えやすい）
  • DRY
  • メタプログラミング的

といった利点があるコードは、暗黙の前提が多くなる。そのため、生成AIはそのようなコードを好まない。

ここでの暗黙の前提とは、「このクラスは本当にx, y, z だけ?」「順序は保証されてる?」「将来属性が増えたらどうなる?」などのようなことを指す。

3. 「初心者」に読みやすいものを優先する

生成AIはデフォルトで「初学者が読んで理解できるか」を重視し、「賢く見えるコード」より「事故らないコード」を好む。例えば:

  • 変数名に意味がある
  • デバッグしやすい
  • 行番号と対応が明確

一方、設計として高度なコードは（初心者にとって）:

  • 変数が抽象的なものを指していて、具体的には何であるか追う必要がある
  • デバッグしにくい（例えば、ラムダ式、ジェネレータ式は遅延実行されるため実行順序を把握しにくい）
  • エラーが起きた時に、原因がどの軸なのか分かりにくい

4. 間違いを避ける

そして、生成AIは、多くの人間と同様に、誰かに怒られることを恐れている。ChatGPTの主張を次に引用する:

重要なのはここです。生成AIは、

  • 賢く見える最短コード
  • 拡張性のある設計

よりも、「誰に渡しても怒られにくいコード」を優先します。

あなたの書き方は:

  • 設計者視点
  • 抽象化に価値を見出す人向け
  • ライブラリ内部や研究コード向き

生成AIの書き方は:

  • サンプルコード
  • 教育用途
  • Q&A回答向き

ああ、なるほど。それならバイブコーディングが行き詰まるのも納得だ。もし、人間がこのような指針でコードを書いていたら、ある程度の規模になった段階で必ず行き詰まるだろう。何度も経験したから、とてもよくわかるよ。

しかし、ChatGPTは、次のようなプロンプトを与えれば生成するコードを改善できると、ついでに主張してきた。

DRYを重視し、将来…が変わっても対応できる実装にしてください

将来変わりそうなのが何か分からないなら、この仕事は任せられないんだけどね。とにかく、何か指示すれば「もっと良い」コードを生成できるらしい。

残念なことに、実際のところ、それを信じてそのようなプロンプトを書いても、成功する可能性は少ない。根本的な問題は、学習データに含まれる高度なコードの割合が少ない、ということだ（というか、高度なコードの割合はそもそも少ない）。「三つ子の魂百まで」のように、若いときに貧乏だと歳をとって裕福になっても貧乏性だけは変わらない、ようなことはよくある。それと似たようなもので、生成AIは初心者向けのコードばかり学習してきたので、そういうコードを出しがちな（つい出てしまう）体質だと考えて良い。

しかし、健康に悪いことは完璧に理解しているのにタバコをやめられないあの人のように、生成AIの行動（出力）が彼らの理解（知識）に伴わないのは、いったい何故か。生成AIは何かの依存症に罹患しているわけじゃないだろう。

ポチョムキン理解

ポチョムキン理解（Potemkin Understanding）[1] とは、AIが「表面上は完璧に理解しているように見えるが、実際には中身を伴っておらず、応用や一貫した推論ができない」現象を指す。詳細についてはリンク先の論文をChatGPTにでも要約させて調べてもらいたい。

なお、ポチョムキン理解という用語は、STAP細胞のようなものと異なり、新規に発見された現象に新しく付けられた名前ではない。展開されたコードではないが、多くの人が知っているが名前が無かった現象である。今後はポチョムキン上司、ポチョムキン新入社員などが出現する可能性が高いが、彼らははるか昔から存在している。

というのは、この概念はLLMだけではなく、人間でも当てはまる。例えば、ほとんどのデザインパターンは理解していて説明もできるのに、ゴミのようなコードしか書けない輩を私はたくさん見てきた。現代の生成AIはそうした連中と同じく、上っ面はエリートのようだが中身が無い人間のようなものなのだ。

また、この論文では次のようなLLMを対象にしており、現時点では積極的には利用しない型落ちしたモデル名が並んでいる。

Our analysis spans the following 7 models: Llama-3.3 (70B), GPT-4o, Gemini-2.0 (Flash), Claude3.5 (Sonnet), DeepSeek-V3, DeepSeek-R1, and Qwen2-VL (72B).

だからといって、より最新のLLMを使っているのでポチョムキン理解とは関係無いだろうと判断するのは早計だ。 文献[1]で興味深かったトピックをいくつか紹介しておく。

LLMのベンチマーク

LLMの一部のベンチマークは、AP試験（アメリカの大学単位認定試験）や数学の競技大会、プログラミングテストなど、既存の「人間向けのベンチマークテスト」で高得点を取ることを良しとしている。ChatGPTの最新モデルがどこぞの大学の入学試験で合格水準に達した、というニュースを聞いたことがあるかもしれないが、それもそれらのベンチマーク結果に由来している。

人間向けのベンチマークテストには、次のような前提がある。

  • 人間の間違い方（誤解）のパターンは限定的で、構造化されている

人間相手に試験を考える側は「ここを根本的に理解していないと、こう間違えるはずだ」という予測を立てる。良い試験は「本当に理解している人間しか正解できない」ように上手く設計されている。したがって、このような人間向けの試験をLLMに課して結果をベンチマークする場合、次のような前提が成り立つ必要がある。

  • LLMも人間と同じようなパターンで概念を誤解する

つまり、人間向けのベンチマークテストをLLMに用いるということは、「人間もLLMも同じように理解するので、間違い方のパターンも共通である」という前提を置いたことになる。

だが、もしLLMが、人間とは全く違う仕組みで理解し、全く違うパターンで誤解するのだとしたら、人間向けの試験にたまたま正解できたとしても、それが人間と同じように概念を理解していることにはならない。

文献[1]では、LLMが人間とは異なる理解の仕方をしている場合、試験の高得点は、実は、表面的な張りぼてに過ぎないということを指摘している。一見すると見事に理解しているようにみえる（テストには正解する）が、いざやらせてみると人間なら絶対にしないようなトンチンカンな間違いをする、ということである。

例えば、アナウンサーやコメンテーターが上手にスポーツの実況中継や解説ができるからといって、彼らがそのスポーツ自体を上手にプレイできるかどうかは別である。LLMのベンチマークに人間向けの試験を流用するのは、それを混同するようなものである。

最後に

私は生成AIにコードを書かせることに否定的ではなく、むしろ肯定的に捉えている。世の中には、公文式の算数の教材の解答欄を埋めるようなソフトウェア開発の仕事が、未だに尽きない。そのような仕事には生成AIが適任だ。というよりも、そんなものは元々人間がやるべきことだったのか、疑問に思うことが、まだまだたくさんある。そして、ダイクストラ法で最適解が求まるような問題を生成AIに解かせている人たちとか、自覚のない地球温暖化推進派が増殖中だ。

LLMが人間と同じように理解しているかどうかは別として、LLMが便利に使える局面でそれを使わないのは愚行である。強盗がバールのようなもので押し入ったという事件があったとしても、強盗がテコの原理を知っていたかどうかなど問題ではないのだ。人間と似て非なるLLMは、人の会話を模倣するように作られたハリボテかもしれないが、24時間働かせても病気になったりしない。我々が人のようなもので「押し入ることができる所」は、いくらでもありそうだ。

人類は空に太陽があれば昼、なければ夜として、夜に太陽の代わりとなる灯りを発明してきた。火、松明、電球など。エジソンはオームの法則を知らずに電球を発明したが、ポチョムキン理解と批判されたりしないだろう。太陽と違う仕組みで明かりをもたらしても、本物と違う仕組みで光っているので使わないという奴はいなかったはずだ。太陽が光を放つ仕組みがわかったのは、電球の発明と比べても、つい最近だからだ。

確かに、人類は「LLMがどう理解を実現しているのか」をよく分かってない。それどころか、そもそも人類は、自分たちの脳がどのように意識を理解しているのか、思考、理解、創造性の正体、感情の統合的な仕組み、なぜニューロンネットワークの回路で知能が成立するのかも、未だにほとんどわかっていない。

便利なものは使う。ただし、どう使うかはよく考えて使うべきだ。

AGIが実現すれば、このような憂慮は無意味かもしれない。しかし、何の根拠もないが、今のLLMの技術的延長上にAGIの実現は無いと思う。なので、これからしばらくはVibe Code Cleanup Specialistという職業が重要になるだろう。
